# Новое доменное событие

Контракт: [rules/PLATFORM.md §10](../../../rules/PLATFORM.md);
надёжность: [rules/BACKEND_RULES_PRODUCTION.md](../../../rules/BACKEND_RULES_PRODUCTION.md) §9, §11, §20.

## Шаг 0 — проверить, что событие уместно
Событие — **свершившийся факт**, не команда (правило 71). Если нужен запрос-ответ или
синхронная операция — это вызов публичного протокола через DI, не событие. Если продюсер
хочет «сказать консьюмеру, что делать» — контракт спроектирован неверно.

## Шаг 1 — контракт события
- **Имя:** `<domain>.<entity>.<action>` в прошедшем времени: `orders.order.created`.
- **Payload:** Pydantic-схема в `apps/<domain>/events.py` продюсера — это публичный
  контракт домена. Класть в payload факты (id + данные, нужные консьюмерам), не ORM-дамп.
- **Версия:** `eventVersion` в конверте. Эволюция только аддитивная (новые опциональные
  поля); breaking → новое имя/версия (`...created.v2`), старая живёт, пока есть консьюмеры.
- **Конверт:** `messageId` (UUID), `eventName`, `eventVersion`, `occurredAt` (UTC),
  `correlationId` (пробрасывается из текущего запроса, правило 15).

## Шаг 2 — публикация (продюсер)
- **Только через Transactional Outbox** (правило 75): запись события в таблицу `outbox`
  в ТОЙ ЖЕ транзакции (через UoW), что и доменное изменение. Прямой publish в брокер из
  use case (dual-write) — запрещён.
- Relay/poller читает outbox и публикует в брокер, помечая отправленное.

## Шаг 3 — потребление (консьюмер)
- Консьюмер зависит **только от схемы события** (правило 74), не от internals продюсера.
- **Идемпотентность обязательна** (правило 76): дедуп по `messageId` (inbox-таблица) —
  доставка at-least-once, повторы будут.
- Обработчик — «контроллер»: достаёт use case из DI (REQUEST-scope на сообщение,
  правило 77) и вызывает его. Бизнес-логики в обработчике нет.
- Ошибки: retry с backoff; «ядовитое» сообщение после N попыток — в DLQ, не бесконечный цикл.

## Шаг 4 — тесты
- Схема события: сериализация/десериализация, конверт полный.
- Продюсер: доменное изменение и outbox-запись атомарны (падение между ними невозможно).
- Консьюмер: повторная доставка того же `messageId` не даёт дублей.

## Верификация
- [ ] Имя в прошедшем времени, payload — версионируемая схема в `events.py`
- [ ] Публикация через outbox в одной транзакции; dual-write отсутствует
- [ ] Консьюмер идемпотентен, DLQ настроен, scope на сообщение
- [ ] Сверить по разделам «События и брокер», «Фоновая работа» из
      [rules/RULES_CHECKLIST.md](../../../rules/RULES_CHECKLIST.md)
