# Планирование продукта (идея → доставка по фазам)

Превратить сырую идею в план, который full-stack-сборка может выполнить почти под ключ, соблюдая
**весь свод правил**. План живёт в `plans/`; каждая фаза затем выполняется скиллами сборки
([new-domain](../new-domain/SKILL.md), [new-endpoint](../new-endpoint/SKILL.md),
[new-event](../new-event/SKILL.md), [new-frontend-section](../new-frontend-section/SKILL.md))
и проходит гейт [rules-review](../rules-review/SKILL.md).

**Сначала прочитать:** [rules/README.md](../../../rules/README.md) (карта),
[rules/PLATFORM.md](../../../rules/PLATFORM.md),
[rules/RULES_CHECKLIST.md](../../../rules/RULES_CHECKLIST.md),
[rules/GIT_AND_DELIVERY.md](../../../rules/GIT_AND_DELIVERY.md). Это стек
**FastAPI + Next.js** — планировать внутри него, а не в обход.

## Шаг 0 — понять идею (согласовать с пользователем)
- **Что** за продукт/фича; **кто** пользователи и клиенты (web, mobile,
  интеграции — API обслуживает их всех, [PLATFORM §1](../../../rules/PLATFORM.md)).
- **Ключевые user stories** — вертикальные срезы. Отделить обязательное (MVP) от более позднего.
- **Нефункциональные потребности:** модель identity/аутентификации ([PLATFORM §5](../../../rules/PLATFORM.md)),
  масштаб (вспомнить [§3](../../../rules/PLATFORM.md): сотни, а не миллионы — модульный монолит),
  внешние интеграции, события между доменами.
- **Явные не-цели.**
Спрашивать только то, что нельзя разумно вывести самому; предлагать разумные значения по умолчанию, а не устраивать допрос.

## Шаг 1 — очертить доменную модель
- Перечислить **bounded contexts (домены)** и их **сущности**. Домен зависит от другого
  только через его публичный **протокол** или **событие**, никогда через импорт internals
  (правила 41–44).
- Определить **поверхность API-контракта** — эндпоинты по доменам, спроектированные от домена,
  а не от экрана (правила 1–2).
- Назвать **модель identity**, основные **сценарии ошибок** и где **события** интегрируют домены.

## Шаг 2 — декомпозировать на фазы
Выстроить последовательность так, чтобы каждая фаза была **поставляемой и соответствующей правилам**. Канонический порядок:

1. **Фундамент** — скелет проекта ([BACKEND_STRUCTURE](../../../rules/BACKEND_STRUCTURE.md)):
   `core`, настройки, dishka-контейнер, `health`, CI и
   рабочий процесс [GIT_AND_DELIVERY](../../../rules/GIT_AND_DELIVERY.md) (trunk-based, PR, релиз).
2. **Identity и аутентификация** ([PRODUCTION §1–2](../../../rules/BACKEND_RULES_PRODUCTION.md)) — если продукту это нужно.
3. **Домены** — по одному bounded context за раз (`new-domain`), сначала самый ценный срез;
   добавлять эндпоинты как вертикальные срезы (`new-endpoint`).
4. **Кросс-доменные события** (`new-event`) там, где домены интегрируются.
5. **Frontend-поверхности** (`new-frontend-section`), когда контракт стабилен — типы берутся
   из OpenAPI-схемы ([FRONTEND_STRUCTURE](../../../rules/FRONTEND_STRUCTURE.md)).
6. **Production-упрочнение** ([PRODUCTION](../../../rules/BACKEND_RULES_PRODUCTION.md) критично):
   наблюдаемость, идемпотентность, rate limits, деплой.

Каждая фаза называет: **скилл сборки** для запуска, **разделы правил** в её объёме и
**критерии готовности** (тесты + typecheck + зелёный `rules-review`, чистый OpenAPI-дифф).

## Шаг 3 — записать план в `plans/`
- **`plans/PLAN.md`** — план по фазам: фазы, срезы, порядок, скилл сборки на каждый шаг, критерии готовности.
- **`plans/DECISIONS.md`** — ключевые архитектурные решения с обоснованием (в стиле ADR).
- **`plans/design/<topic>.md`** — более глубокий дизайн по домену/теме по мере надобности.

Продуктовые правила и доктрины живут в **`plans/`**, никогда в `rules/` — свод правил
остаётся продукт-агностичным (см. [rules/README.md](../../../rules/README.md)).

## Шаг 4 — передать в разработку
- **Подтвердить план** с пользователем до написания кода.
- Выполнять **фаза за фазой**: подходящий скилл сборки на каждый срез; запускать `rules-review`
  перед каждым мерджем; следовать `GIT_AND_DELIVERY` на каждый срез (ветка → PR → squash).
- Держать `plans/PLAN.md` в актуальном состоянии по мере завершения фаз (отмечать пункты, фиксировать отклонения).

## Верификация — хороший план
- [ ] Каждая user story отображается на срез внутри фазы.
- [ ] Домены изолированы; интеграции идут через протокол или событие (правила 41–44).
- [ ] Contract-first: эндпоинты спроектированы от домена, а не от экрана (правила 1–2).
- [ ] У каждой фазы есть явные критерии готовности и названный скилл сборки.
- [ ] Нефункциональные аспекты (аутентификация, наблюдаемость, деплой) вводятся по фазам, а не забыты.
- [ ] План живёт в `plans/`; `rules/` остаётся продукт-агностичным.
