# Новый endpoint (вертикальный срез)

Правила: [rules/BACKEND_RULES.md](../../../rules/BACKEND_RULES.md) §4–§7, §11;
[rules/PLATFORM.md](../../../rules/PLATFORM.md) §1, §3–§5.

## Шаг 0 — сформулировать user story
Один endpoint = одна user story = один UseCase (правило 21). Сформулировать: «кто,
что делает, что получает». Проверить multi-client тест (правило 1–2): эндпоинт
описывает предметную область, а не экран конкретного фронта.

## Шаг 1 — спроектировать контракт
- Путь: `/{entities}` (мн. число), метод по семантике; путь под текущей версией API.
- Request/Response-схемы: `camelCase` наружу, `extra="forbid"`, никаких
  `id`/`role`/`is_admin` от клиента (правило 32).
- Изменение существующего контракта? Проверить совместимость: breaking → новая версия
  пути (правило 10).
- Ошибки: какие доменные исключения бросаются, на какие HTTP мапятся (уже есть базовые
  в `core` — не плодить дубли).

## Шаг 2 — реализовать снизу вверх
1. **Repository** — нужен новый запрос? Добавить метод в `Protocol` + `Impl`
   (DTO in/out, flush без commit). Обязательные параметры до `*`, флаги после.
2. **Service** — переиспользуемая логика/инварианты. Если логика одноразовая — можно
   прямо в use case, не раздувать сервис искусственно.
3. **UseCase** — `Protocol` + `Impl`, `async def __call__`; проверка прав и владения
   ресурсом ЗДЕСЬ (правила 81–82); возвращает Response-схему.
4. **Provider** — привязка нового use case в `providers.py` домена.
5. **Router** — `@inject`, `FromDishka[UseCaseProtocol]`, без логики; пагинация
   больших списков — keyset/cursor (правило 97).

## Шаг 3 — транзакции и побочные эффекты
- Мутация одного агрегата — транзакция запроса (провайдер коммитит сам).
- Несколько репозиториев — Unit of Work (правило 29).
- Публикация события — через outbox в той же транзакции (→ скилл `new-event`).
- Критичный POST (платёж, создание заказа) — рассмотреть `Idempotency-Key` (правило 95).

## Шаг 4 — тесты
- Unit на use case (in-memory протоколы): happy path + ошибки прав/валидации.
- Тест на маппинг доменной ошибки в HTTP-код и конверт `{error, message, details}`.

## Верификация
- [ ] В роуте нет логики; в use case есть проверка прав/владения
- [ ] Контракт совместим или версия поднята; `/docs` корректен
- [ ] Транзакционная граница выбрана осознанно (запрос / UoW)
- [ ] Сверить diff по разделам «Слои», «Ошибки», «Безопасность» из
      [rules/RULES_CHECKLIST.md](../../../rules/RULES_CHECKLIST.md)
