# Production best-practices (дополнение к BACKEND_RULES.md)

> Дополнение к [BACKEND_RULES.md](BACKEND_RULES.md). Базовые правила покрывают
> **архитектуру кода** (чистая архитектура, слои, репозитории, модели, dishka, ошибки).
> Этот документ покрывает **production-эксплуатацию**: безопасность, наблюдаемость,
> отказоустойчивость, операционную работу с данными и деплой. Сквозные платформенные
> контракты (единый формат ошибки, версионирование API, модель идентичности для всех
> клиентов) — в [PLATFORM.md](PLATFORM.md).
>
> Ссылки вида «§N» указывают на разделы базового файла. Новые правила опираются на
> уже принятый стек: identity/сессии/локи — через **dishka-провайдеры и scope**,
> authz — в доменном слое, outbox — поверх существующего **Unit of Work**,
> stampede-lock — поверх распределённого Lock из core.
>
> Приоритеты: **Критично** (без этого нельзя в прод) → **Важно** (зрелый сервис) →
> **Желательно** (повышает зрелость, контекстно-зависимо).

# Часть I. Критично

## 1. Аутентификация и авторизация

В базовых правилах есть `PermissionDenied → 403` (§11) и `SECRET_KEY` (§12), но нет
правил, **где в чистой архитектуре живёт authn/authz**. Это критичный пробел.

### AuthN (аутентификация)
- **Отдельный домен `apps/auth/`** с эталонной структурой домена (§3).
- **JWT access-токен** — короткий TTL (5–15 мин) + **refresh-токен с ротацией**.
  Для отзыва хранить `jti` (или whitelist refresh-токенов) в Redis/БД — без этого
  токен нельзя инвалидировать до истечения.
- **Хеширование паролей — Argon2id** (`argon2-cffi` или `pwdlib`), параметры по OWASP.
  Никогда не sha/pbkdf2/md5 вручную. (`passlib` сейчас слабо поддерживается.)
- **OAuth2 / OIDC** — `authlib` (внешние провайдеры, single sign-on).
- Библиотека JWT — `pyjwt` или `joserfc`.

### AuthZ (авторизация)
- **Проверка прав — в UseCase/Service-слое, НЕ в роутере.** Роутер только извлекает
  identity из токена; решение «можно ли» — доменное правило. `PermissionDenied`
  (§11) бросается из домена (см. §6 базовых правил — бизнес-логика в UseCase).
- **RBAC** (роли) как база; **ABAC**/policy (`oso`/`casbin`) — для сложных правил.
- **BOLA (object-level)** — проверять **владение конкретным ресурсом** в каждом
  UseCase, а не только факт аутентификации (см. §2 — это OWASP API #1).

### Где брать текущего пользователя
- **`CurrentUser` — через dishka REQUEST-scope провайдер** (§10), а не глобальный
  `contextvars`/синглтон. Провайдер достаёт identity из токена запроса; UseCase/Service
  получают `CurrentUser` как обычную зависимость.

```python
# dishka-провайдер identity (REQUEST scope)
@provide(scope=Scope.REQUEST)
def current_user(self, request: Request, auth: AuthServiceProtocol) -> CurrentUser:
    token = extract_bearer(request)
    return auth.identify(token)          # бросает AuthenticationError при невалидном
```

**Почему критично:** authn/authz «прикрутить потом» = переписать слои доступа и
протечь проверки прав по контроллерам.

## 2. Безопасность API (OWASP API Security Top 10)

Базовые правила упоминают только `CORS (allow_origins)` (§12). Нет защиты от перебора,
заголовков безопасности, защиты от типовых атак на API.

| Угроза | Правило |
|---|---|
| **Брутфорс / DoS** | **Rate limiting** — `slowapi` или middleware на Redis (sliding window / token bucket). Жёсткие лимиты на `login`/`refresh`/`forgot-password`. |
| **Заголовки** | **Security headers** (`secure`-библиотека или middleware): `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy`, `Referrer-Policy`. Убрать `Server`-заголовок. |
| **CORS** | Явный allowlist origins. **Запрещено** `allow_origins=["*"]` вместе с `allow_credentials=True`. |
| **CSRF** | Для web-клиентов на cookie-сессии: `SameSite=Lax/Strict` + CSRF-токен на мутирующие запросы (см. PLATFORM §5). Bearer-клиентов не касается. |
| **BOLA (#1)** | Проверка владения ресурсом в каждом UseCase (см. §1). Аутентификация ≠ авторизация на объект. |
| **BOPLA / mass assignment** | Pydantic-схемы строгие: `model_config = ConfigDict(extra="forbid")`. Отдельные Create/Update-схемы (§7 базовых) — не принимать `id`/`role`/`is_admin` от клиента. |
| **Unrestricted consumption** | Лимиты размера тела запроса, глубины пагинации, числа элементов в bulk. |

**Почему критично:** BOLA — главная причина утечек в API; mass assignment через
незакрытые Pydantic-схемы — тихая дыра на повышение привилегий.

## 3. Наблюдаемость: структурные логи и correlation id

Базовые правила инициализируют логирование (§3), но без структуры и трассировки запроса.

- **Структурные JSON-логи** — `structlog` (предпочтительно) либо stdlib `logging`
  с JSON-форматтером. Никаких `print` и неструктурированных строк в проде.
- **Correlation / Request ID** — middleware (`asgi-correlation-id`), который
  принимает/генерирует `X-Request-ID`, кладёт его в `contextvars` и подмешивает
  в **каждую строку лога и каждую ошибку**. Прокидывать дальше в исходящие HTTP/брокер.
- **Запрет PII/секретов в логах** — явный список редактируемых полей
  (`password`, `token`, `authorization`, при необходимости `email`).
- Логи — в **stdout** (12-factor), не в файл; агрегатор собирает оттуда (см. §5).

**Почему критично:** без request_id и структурных логов инцидент в проде нерасследуем —
строки одного запроса невозможно связать в распределённой системе.

## 4. Graceful shutdown и таймауты

В базовых правилах `lifespan` упомянут только для закрытия dishka-контейнера (§10).

### Graceful shutdown
- Корректная обработка **SIGTERM**: дождаться завершения in-flight запросов, затем
  в `lifespan`-shutdown закрыть пулы БД/Redis/брокера, **dishka-контейнер**
  (`await container.close()`), остановить APScheduler и FastStream-консьюмеры.
- В k8s: `terminationGracePeriodSeconds` ≥ времени долгих запросов + `preStop`-hook
  (короткая пауза, чтобы LB успел убрать pod из ротации).

### Таймауты — на всё
- **HTTPX-клиент всегда с явным `timeout=`** (connect/read/write/pool). Дефолтный
  «без таймаута» запрещён.
- **БД** — `statement_timeout` на сессии/пуле (защита от зависших запросов).
- **Внешние вызовы** оборачивать в `asyncio.timeout(...)`.

**Почему критично:** релиз без graceful shutdown = оборванные запросы и потерянные
транзакции при каждом rollout. Запрос без таймаута выжирает пул и кладёт сервис.

## 5. Production-деплой (образ и k8s)

Базовые правила описывают Dockerfile и docker-compose для инфраструктуры (§16/§17),
но не production-образ и не манифесты.

### Dockerfile
- **Multi-stage**: builder (`uv sync --frozen --no-dev`) → slim runtime-образ.
- **Non-root**: создать пользователя, `USER appuser`. Read-only rootfs где возможно.
- Базовый образ **запинен по digest** (`python:3.13-slim@sha256:...`).
- Миграции в образ попадают (§3 базовых), dev-артефакты — нет (`.dockerignore`).

### Kubernetes
- **Раздельные probes** (не один «200-healthcheck»):
  - **liveness** — shallow: процесс жив, **без проверки зависимостей** (иначе флап БД
    рестартит поды).
  - **readiness** — deep: БД/Redis/брокер доступны (см. §16).
  - **startup** — для медленного старта (миграции/прогрев).
- **`resources.requests/limits`** (CPU/mem) — обязательно.
- **12-factor**: stateless-процессы, конфиг из env (§12 базовых), логи в stdout
  (не в `logging.dev`-файл в проде).

**Почему критично:** root-контейнер и единый healthcheck — классические причины
эскалации привилегий и каскадных рестартов всего деплоймента при моргании БД.

# Часть II. Важно

## 6. Метрики и трейсинг

В core упомянут Prometheus (§13 базовых) и опциональный `SENTRY_DSN` (§12), но без правил.

- **Метрики** — `prometheus-fastapi-instrumentator`: RED (Rate/Errors/Duration) +
  эндпоинт `/metrics`. Бизнес-метрики — отдельным registry.
- **Трейсинг** — **OpenTelemetry** (`opentelemetry-instrumentation-fastapi`,
  `-sqlalchemy`, `-httpx`), span'ы связаны с тем же correlation id (§3).
- **Sentry** — сделать стандартом (не опцией), с привязкой к `request_id` и
  `release`-версии из semantic-release (§14 базовых).

**Почему важно:** без метрик нет SLO/алертинга; без трейсинга непонятно, где
латентность в цепочке сервисов.

---

## 7. Soft delete и аудит

§18 базовых упоминает `deleted_at` только в чеклисте; в §8 (модели) его нет, и нет
правил, **как с ним жить**.

- **`SoftDeleteMixin (deleted_at: datetime | None)`** — мягкое удаление.
- **Репозиторий по умолчанию фильтрует** `deleted_at IS NULL`; флаг `with_deleted=True`
  отключает фильтр явно.
- **Partial unique index**: `UNIQUE (...) WHERE deleted_at IS NULL` — иначе уникальность
  ломается после soft-delete (нельзя пересоздать «удалённую» запись).
- **Аудит** — `created_by` / `updated_by` (UUID из `CurrentUser`, §1), заполняется в
  Service/UoW-слое. Для полной истории изменений — таблица истории / триггеры /
  `sqlalchemy-continuum`.
- **Soft delete ≠ стирание (PII/GDPR).** По запросу на удаление данных или истечении
  срока хранения PII **физически удаляется или анонимизируется** — включая аудит,
  историю и связанные записи. Сроки хранения (retention) определяются по сущностям;
  «мягко удалили и храним вечно» для персональных данных — нарушение.

**Почему важно:** «забыли отфильтровать удалённые» и «сломалась уникальность после
soft-delete» — массовые баги; аудит «кто изменил» нужен для комплаенса.

## 8. Конкурентность: блокировки и изоляция

§8 базовых не упоминает конкурентный доступ. Generic CRUD `update` (§7) без версии =
lost update под нагрузкой.

- **Оптимистичная блокировка** — колонка `version_id` +
  `__mapper_args__ = {"version_id_col": version}` (SQLAlchemy сам делает
  `WHERE version = :v` и бросает `StaleDataError`). Дефолт для конкурентных апдейтов.
- **Пессимистичная** — `SELECT ... FOR UPDATE` для критичных мест (балансы, счётчики).
- **Уровень изоляции** — дефолт `READ COMMITTED`; поднимать до `REPEATABLE READ`/
  `SERIALIZABLE` точечно, где нужна защита от phantom/non-repeatable read.

**Почему важно:** без этого два параллельных апдейта молча затирают друг друга.

---

## 9. Идемпотентность мутаций

§7 базовых даёт `upsert ON CONFLICT`, но нет идемпотентности на уровне API/событий.

- **`Idempotency-Key`** — заголовок для POST (платежи, создание заказов). Middleware
  сохраняет `ключ → результат` в Redis с TTL; при повторе возвращает сохранённый ответ.
- **Идемпотентные консьюмеры** событий — дедуп по `message_id` (inbox-таблица, §11).

**Почему важно:** ретраи клиентов и брокеров неизбежны; без идемпотентности — двойные
списания и дубликаты.

---

## 10. API design: версионирование, пагинация, фильтрация

§7 базовых даёт пагинацию в репозитории и camelCase, но не стандарт API.

- **Версионирование** — префикс пути **`/api/v1/`**. Правило breaking changes для API
  (по аналогии с SemVer из §14): несовместимое изменение → новая версия пути.
- **Keyset/cursor-пагинация** как дефолт для больших списков — offset деградирует на
  больших таблицах и «прыгает» при вставках. Ответ `{items, next_cursor}`.
  `fastapi-pagination` или собственная схема.
- **Фильтрация/сортировка** — единый контракт query-параметров (`fastapi-filter`),
  не ad-hoc на каждом эндпоинте.

**Почему важно:** offset-пагинация и отсутствие версионирования — дорогой техдолг
после публикации API.

---

## 11. Outbox pattern и надёжные сообщения

В стеке есть FastStream (§1 базовых), но нет правил надёжной публикации. Запись в БД +
публикация в брокер = классическая **dual-write** проблема (событие теряется при падении
между commit и publish).

- **Transactional Outbox** — событие пишется в таблицу `outbox` в **той же транзакции**,
  что и доменное изменение (используем существующий **UoW**, §6 базовых). Отдельный
  relay/poller читает `outbox` и публикует в брокер, помечая отправленное.
- **Идемпотентные консьюмеры** + **inbox**-таблица для дедупа (§9).
- **DLQ** (dead letter queue) для «ядовитых» сообщений + retry с backoff (§15).

**Почему важно:** без outbox события теряются → рассинхрон состояния между сервисами.

---

## 12. Кэширование

Redis есть в инфраструктуре (§16) и cache-репозиторий в core (§13), но нет паттернов.

- **Cache-aside** как стандарт: read → cache → miss → db → заполнить cache;
  write → инвалидировать ключ.
- **Обязательный TTL** на всё — вечных ключей нет.
- **Stampede protection** — при истечении популярного ключа не пускать всех в БД:
  распределённый **Lock из core** (§13) на перестроение или early recompute.
- **Инвалидация по доменным событиям**, а не «на глаз».

**Почему важно:** кэш без TTL/инвалидации отдаёт устаревшие данные; cache stampede
кладёт БД при истечении горячего ключа.

---

## 13. Тестирование

§15 базовых даёт pytest + фикстуру `alembic upgrade head` (медленно, на каждый тест).

- **testcontainers-python** — интеграционные тесты на реальном Postgres/Redis в
  изолированном контейнере (вместо общей dev-БД).
- **Фабрики данных** — `polyfactory` (нативно для Pydantic/SQLAlchemy) вместо ручных
  фикстур.
- **Пирамида тестов** явно: **много unit** (домен без I/O дёшев — Protocol + in-memory
  репозитории, §5/§7 базовых), **меньше интеграционных**, **минимум e2e**.
- **Контрактные тесты** — `schemathesis` (фаззинг против OpenAPI); `pact` для
  consumer-driven при микросервисах.
- **Откат на savepoint** вокруг теста вместо полного `upgrade head` — кратно быстрее.

**Почему важно:** медленные/хрупкие тесты не запускают. Чистая архитектура уже даёт
дешёвые unit-тесты — это надо зафиксировать как правило.

---

## 14. Secrets management и SAST/SCA

§12 базовых — секреты только через `.env`; §17 CI — линт+тесты без security-сканов.

- **Прод-секреты** — из vault/secrets-manager (HashiCorp Vault, AWS/GCP Secrets Manager,
  k8s Secrets), не из `.env`-файла на диске. `.env` — только локальная разработка.
- **Pre-commit**: `detect-secrets` / `gitleaks` — не дать закоммитить секрет.
- **CI security-сканы**: `bandit` (SAST для Python), `pip-audit` (CVE в зависимостях),
  Renovate/Dependabot (апдейты), `trivy`/`grype` (скан Docker-образа).

**Почему важно:** утёкший секрет в git и уязвимая транзитивная зависимость — самые
частые инциденты безопасности.

# Часть III. Желательно

## 15. Retry с backoff и circuit breaker

- **Retry** — `tenacity`: экспоненциальный backoff + **jitter**, только на
  **идемпотентные** внешние вызовы и только на таймауты/5xx.
- **Circuit breaker** — `pybreaker`/`purgatory`: размыкать цепь при серии ошибок
  зависимого сервиса, чтобы не множить нагрузку и не падать каскадом.

**Почему:** ретраи без backoff/jitter усиливают аварию (retry storm); без circuit
breaker падение одной зависимости тянет весь сервис.

---

## 16. Healthcheck: deep vs shallow

Детализация §5 нового файла как отдельное правило (грубое «healthcheck → 200» из §3
базовых недостаточно):

- **`/health/live`** — liveness: процесс жив, **без зависимостей**.
- **`/health/ready`** — readiness: проверяет БД/Redis/брокер; pod выводится из ротации
  при недоступности зависимости, но **не рестартится**.

---

## 17. DDD-тактика (для сложных доменов)

Архитектура уже DDD-light (bounded contexts = `apps/`, UoW). Для сложных доменов —
опционально (для простого CRUD это оверинжиниринг):

- **Value Objects** — Pydantic `frozen=True` модели (Email, Money, типизированные id)
  вместо примитивов.
- **Доменные события** — естественно ложатся на Outbox (§11).
- **Агрегаты** — граница транзакционной консистентности: **UoW = один агрегат за
  транзакцию**.

---

## 18. Нагрузочное тестирование и тюнинг пула

- **Нагрузочные тесты** — `locust`/`k6` перед релизом критичных эндпоинтов.
- **Тюнинг async engine** — явные `pool_size` / `max_overflow` / `pool_timeout` /
  `pool_pre_ping` под ожидаемую нагрузку (в core сейчас только «пул как singleton», §13).

**Почему:** дефолтный пул из 5 соединений упирается в потолок на первом всплеске трафика.

---

## 19. DB-констрейнты как защита данных

В дополнение к `index=True`/FK (§8 базовых):

- **`CHECK` / `UNIQUE` / `NOT NULL` на уровне БД**, а не только Pydantic-валидация.
- Бизнес-инварианты, выразимые в БД, должны быть в БД — **приложение не единственный
  писатель** (миграции, сырой SQL, другие сервисы).

---

## 20. Фоновая работа: воркеры, консьюмеры, планировщик

> Приоритет: **Важно** — актуально с первого консьюмера или cron-задачи.

- **Тот же DI-контейнер, что и HTTP.** Воркеры, FastStream-консьюмеры и APScheduler
  не собирают зависимости руками: на каждое сообщение/джобу открывается
  **REQUEST-scope** dishka-контейнера (сессия, репозитории, use cases — как в запросе).
- **Cron-задачи — под распределённым локом** (Lock из core, §13 базовых): при N
  репликах задача выполняется один раз, а не N.
- **Джоба идемпотентна** (повторный запуск безопасен) и сводится к **вызову use case**.
  Код планировщика/консьюмера — такой же «контроллер», как роутер: бизнес-логики в нём
  нет.
- **Транзакция — явная, на единицу работы** (сообщение/джоба), те же правила владения,
  что в базовых правилах (§7): репозиторий не коммитит, границей владеет
  провайдер/UoW.
- Consumer подчиняется правилам контракта событий ([PLATFORM.md §10](PLATFORM.md)):
  зависит только от схемы события, дедуп по `messageId`, DLQ для ядовитых сообщений.

**Почему важно:** «шедулер, который выполнился на всех репликах» и «консьюмер со своей
самосборной сессией без отката» — типовые источники дублей и полузаписанных данных.

# Быстрые победы (максимум эффекта за минимум усилий)

1. **`structlog` + `asgi-correlation-id`** (§3) — пара часов, радикально меняет
   расследуемость инцидентов в проде.
2. **`extra="forbid"` в Pydantic + проверка владения ресурсом в UseCase** (§2) —
   закрывает два самых частых класса уязвимостей API (BOLA, mass assignment) почти даром.
3. **`bandit` + `pip-audit` + `gitleaks`** в CI/pre-commit (§14) — по строке в конфиге,
   ловят секреты и CVE автоматически.

# Сводка do / don't (production)

**DO**
- AuthZ-проверки в доменном слое (UseCase/Service); `CurrentUser` через dishka REQUEST-scope.
- Argon2id для паролей; короткий access + ротируемый refresh с отзывом.
- Строгие Pydantic-схемы (`extra="forbid"`); проверка владения ресурсом (BOLA).
- Структурные JSON-логи + correlation id; логи в stdout.
- Таймауты на все внешние вызовы и БД; graceful shutdown по SIGTERM.
- Multi-stage non-root Dockerfile; раздельные liveness/readiness probes; resource limits.
- Метрики + трейсинг с общим correlation id; Sentry с release-версией.
- Soft delete с partial unique index и дефолтным фильтром; аудит created_by/updated_by.
- Оптимистичная блокировка на конкурентных апдейтах; осознанный isolation level.
- Idempotency-Key на критичные POST; идемпотентные консьюмеры.
- Версионирование `/api/v1/`; keyset-пагинация; единый контракт фильтрации.
- Outbox поверх UoW; DLQ + retry с backoff для сообщений.
- Cache-aside с TTL и stampede-защитой (Lock из core).
- testcontainers + polyfactory; явная пирамида тестов; savepoint-откат.
- Секреты из vault; bandit/pip-audit/gitleaks/trivy в пайплайне.

**DON'T**
- Проверять права в роутере; держать identity в глобальном contextvars/синглтоне.
- Хранить пароли через sha/pbkdf2/md5; вечные JWT без отзыва.
- Принимать `id`/`role`/`is_admin` из тела запроса (mass assignment).
- `print` и неструктурированные логи; логировать секреты/PII.
- HTTP/БД-вызовы без таймаута; релизить без graceful shutdown.
- root-контейнер; единый «200-healthcheck» на liveness и readiness.
- offset-пагинация на больших таблицах; API без версии.
- Писать в БД и в брокер двумя независимыми операциями (dual-write без outbox).
- Кэш без TTL и без стратегии инвалидации.
- Прод-секреты в `.env`-файле на диске; CI без security-сканов.
