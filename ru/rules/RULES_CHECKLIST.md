> Сжатая выжимка всего свода — одно правило = одна строка. Для ревью кода, PR-чеклиста
> и быстрой сверки. Подробности и обоснования — в полных документах:

## Платформа / API

1. API — продукт для многих клиентов (web, mobile, интеграции), а не деталь одного фронта.
2. Эндпоинты проектируются от предметной области, никогда — под конкретный экран.
3. Платформа проектируется на сотни пользователей, не миллионы: простота и изменяемость важнее горизонтального масштабирования; модульный монолит по умолчанию.
4. Отдельный сервис выделяется только по сильной причине (другой цикл релизов, изоляция отказов), не «на вырост»; тяжёлая инфраструктура (шардирование, mesh, мультирегион) — оверкилл.
5. Единственный контракт клиент↔сервер — опубликованный OpenAPI; в обход API никто не ходит.
6. Типы клиента генерируются из OpenAPI, руками не пишутся; сгенерированное коммитится, CI проверяет свежесть.
7. Breaking change контракта ловится диффом OpenAPI на PR, а не в проде.
8. Наружу — `camelCase`, внутри Python — `snake_case`; конвертируют Pydantic-схемы.
9. Ошибка — единый конверт `{error, message, details}`; клиент ветвится по коду `error`, не по тексту.
10. API версионируется по пути (`/api/v1/`); breaking change = новая версия, старая живёт до вывода.
11. Клиент толерантен: неизвестные поля в ответе игнорирует, не падает.
12. Одна токеновая модель идентичности для всех клиентов (JWT: короткий access + refresh с ротацией).
13. Авторизация — всегда на сервере, в доменном слое; фронт-гейт — только UX.
14. Конфиг из окружения (12-factor); базовый URL API никогда не хардкодится.
15. Correlation/Request ID проходит сквозь всю цепочку: клиент → логи → ошибки → исходящие вызовы и события.
16. Одна сущность называется одинаково везде: БД, DTO, API, события, клиент (ubiquitous language).

## Слои и зависимости (backend)

17. Слои строго вниз: `Router → UseCase → Service → Repository`; инжектить «вверх» запрещено.
18. Зависимость всегда на абстракцию (`Protocol`), не на реализацию (`Impl`).
19. Интерфейсы — через `typing.Protocol` (не ABC); нейминг: `XProtocol` / `XImpl`.
20. В контроллере нет бизнес-логики; в контроллер инжектится только UseCase.
21. Один UseCase = одна user story = один endpoint; это callable-класс (`async def __call__`).
22. UseCase возвращает response-схему, не доменный/ORM-объект.
23. Service — переиспользуемая доменная логика; инжектит другие сервисы и репозитории.
24. Репозиторий инжектит только сессию.
25. Между слоями данные ходят только DTO (Pydantic); в репозиторий входит DTO, из репозитория выходит DTO — ORM-модель никогда не поднимается выше репозитория.
26. Репозиторий инкапсулирует любой I/O: БД, HTTP, Redis, брокер.
27. Репозиторий никогда не делает commit — только flush; транзакцией владеет граница (запрос или UoW).
28. Дефолт — одна транзакция на запрос: commit в session-провайдере при успехе, rollback при исключении.
29. Мутация через несколько репозиториев — только через Unit of Work; UoW владеет транзакцией.
30. Сложные чтения (отчёты, дашборды) — отдельный read-only query-сервис: SQL → сразу Response-DTO, минуя доменные слои; мутации так нельзя.
31. Схемы делятся по назначению: Request/Response (граница use case), Read/Create/Update (граница репозитория).
32. Pydantic-схемы строгие: `extra="forbid"`; `id`/`role`/`is_admin` от клиента не принимаются.

## DI (dishka)

33. DI — только dishka; `fastapi.Depends` как IoC и самописные фабрики запрещены.
34. Привязка `Impl → Protocol` — через `provide(..., provides=Protocol)` в `providers.py` домена.
35. `Scope.APP` — синглтоны (engine, sessionmaker, пулы, конфиг); `Scope.REQUEST` — сессия, репозитории, сервисы, use cases.
36. Сессия и транзакция — через провайдер-генератор (`yield` + commit/rollback).
37. Подмена реализации (Postgres → in-memory) = смена одной привязки, бизнес-логика не трогается.
38. Контейнер собирается в `bootstrap.py`, закрывается в lifespan.
39. Новый домен регистрируется двумя действиями: роутер в агрегатор + Provider в контейнер.

## Домены и структура

40. Каждый домен в `apps/` имеет одинаковую эталонную структуру (router, schemas, use_case, services, repositories, models, exceptions, events, providers).
41. Публичное у домена — только `router`, протоколы сервисов/use case'ов (через DI) и `events.py`; остальное приватно.
42. Домен не импортирует внутренности другого домена (модели, репозитории, `Impl`); взаимодействие — публичный протокол через DI или доменное событие.
43. `core` не импортирует из `apps`; `apps` импортирует `core` — никогда наоборот.
44. Изоляция доменов проверяется автоматически — `import-linter` в CI, не код-ревью «на глаз».
45. Общее для всех доменов — в `core/` (базовые модели, generic CRUD, исключения, провайдеры).
46. Слой одним файлом — только пока сущность одна; вторая сущность → слой папкой с файлом на сущность; use case — файл на user story.
47. Файл ≤ 400 строк — CI-гейт (исключения: миграции, сгенерированное); превысил — дели, а не поднимай лимит.
48. Свалки запрещены: `utils.py`/`helpers.py` в домене не заводятся; общее — в `core` модулем с говорящим именем.
49. Скрипты в корень не класть — только Typer CLI.
50. Тесты зеркалят структуру `src/`.

## Модели БД

51. Модель — единственное число (`User`), таблица — множественное (`users`).
52. PK всегда `id`; предпочтение: UUID v7 → int → UUID v4.
53. Булевы поля — с префиксом `is_`.
54. `created_at`/`updated_at` — всегда; всё время — UTC; всегда `server_default`.
55. Нативные ENUM в БД запрещены — enum на стороне Python, в БД строка/int.
56. Сущность — типизированными колонками, не JSON-свалкой; `JSONB` только как доп. поле (`extra`) для нерегулярных данных; искомые поля — отдельные индексируемые колонки, созревшее поле промотируется из `extra` миграцией.
57. `index=True` на каждый FK; `passive_deletes=True` на relationship.
58. Lazy loading запрещён в async: `lazy="raise"`, связи грузятся явно (`selectinload`).
59. Инварианты, выразимые в БД, — в БД: CHECK / UNIQUE / NOT NULL, не только Pydantic.
60. Soft delete: `deleted_at` + дефолтный фильтр в репозитории + partial unique index.
61. Конкурентные апдейты — оптимистичная блокировка (`version_id`); критичные места — `SELECT FOR UPDATE`.

## Миграции

62. Model First: модели → autogenerate.
63. Все модели импортируются в `env.py`, иначе autogenerate их не видит.
64. Имя миграции — с датой: `год_месяц_день_slug`.
65. Breaking DDL — только expand → contract через отдельные релизы: схема каждого релиза совместима с кодом предыдущего.

## Ошибки

66. Базовые исключения — в `core`, по HTTP-смыслу (`ModelNotFound → 404`); доменные наследуют их.
67. До контроллера — только бизнес-ошибки, после — только HTTP; контроллер — граница превращения.
68. Маппинг в HTTP — централизованные exception handlers, по одному на базовый класс.
69. Доменные исключения — суффикс `Error`.

## События и брокер

70. Событие — такой же публичный контракт, как API: та же строгость к схеме и совместимости.
71. Имя события: `domain.entity.action` в прошедшем времени (`orders.order.created`) — свершившийся факт, не команда.
72. Payload — версионируемая Pydantic-схема в `apps/<domain>/events.py`; эволюция только аддитивная, breaking → новая версия события.
73. Конверт события: `messageId`, `eventName`+`eventVersion`, `occurredAt` (UTC), `correlationId`.
74. Консьюмер зависит только от схемы события, не от внутренностей продюсера.
75. Публикация — только через Transactional Outbox (в одной транзакции с доменным изменением); dual-write запрещён.
76. Консьюмер идемпотентен: дедуп по `messageId` (inbox); «ядовитые» сообщения — в DLQ с retry/backoff.

## Фоновая работа

77. Воркеры, консьюмеры и планировщик используют тот же DI-контейнер; REQUEST-scope открывается на каждое сообщение/джобу.
78. Cron-задача выполняется под распределённым локом — N реплик не выполняют её N раз.
79. Джоба идемпотентна и сводится к вызову use case; бизнес-логики в коде планировщика/консьюмера нет.

## Безопасность

80. Пароли — только Argon2id.
81. Проверка прав — в UseCase/Service, не в роутере; `CurrentUser` — через REQUEST-scope провайдер.
82. Владение конкретным ресурсом проверяется в каждом UseCase (BOLA).
83. Rate limiting на auth-эндпоинты; security headers; CORS — явный allowlist, никогда `*` + credentials.
84. Cookie-сессия web — `SameSite` + CSRF-токен на мутирующие запросы; Bearer-клиентов CSRF не касается.
85. Секреты — write-only: не возвращаются, маскируются, не логируются.
86. Прод-секреты — из secrets-manager, `.env` — только локально.
87. В CI/pre-commit: gitleaks, bandit, pip-audit.
88. Soft delete ≠ стирание: PII по запросу на удаление или истечении retention — hard delete либо анонимизация; сроки хранения определены по сущностям.

## Эксплуатация

89. Логи — структурный JSON в stdout; PII и секреты не логируются; `print` запрещён.
90. Таймауты на всё: HTTP-клиент, БД, внешние вызовы — «без таймаута» запрещён.
91. Graceful shutdown по SIGTERM: дожить in-flight, закрыть пулы и контейнер.
92. Liveness и readiness — раздельные probes (`/health/live` без зависимостей, `/health/ready` — с).
93. Dockerfile — multi-stage, non-root, базовый образ по digest.
94. Retry — только на идемпотентные вызовы, с backoff и jitter; каскады — circuit breaker.
95. Критичные POST — `Idempotency-Key`: повтор возвращает сохранённый ответ.
96. Кэш — cache-aside, всегда с TTL, инвалидация по событиям, stampede-защита локом.
97. Пагинация больших списков — keyset/cursor, не offset.

## Тесты и качество

98. Пирамида: много unit (домен через Protocol + in-memory), меньше интеграционных, минимум e2e.
99. Интеграционные — на testcontainers; фабрики данных — polyfactory; откат — savepoint.
100. Pyright strict + mypy + Ruff + pre-commit — обязательны.
101. Правила сложности Ruff включены (C901, PLR0912/0913/0915); длинная функция рефакторится, а не попадает в исключения.
102. Conventional Commits + semantic-release; версия считается из коммитов.

## Frontend

103. Фронт — один из клиентов API, не привилегированный.
104. Все вызовы API — через единственный `apiFetch`; голые `fetch` по компонентам запрещены.
105. Server Component по умолчанию; `"use client"` — только для интерактива, границу — ниже по дереву.
106. Серверные данные не дублируются в глобальном сторе: один механизм серверного состояния (RSC и/или query-библиотека); глобальный стор — только для чистого UI-состояния.
107. Секреты — только на сервере; в клиентский бандл — только `NEXT_PUBLIC_*`.
108. Страницы тонкие: композиция компонентов, без бизнес-логики.
109. Один компонент = один файл (≤ 300 строк — CI-гейт); разросшаяся логика — в hook отдельным файлом; catch-all `utils.ts` запрещён.
110. Общие примитивы — в `ui/`, не знают про предметную область; специфика — по папкам поверхностей.
111. Поверхности (user/admin) раздельны; кросс-аккаунтная консоль — третья поверхность, не примесь.
112. `app/api/` (BFF) — только посредник, бизнес-логика живёт в backend.
113. Клиентская валидация дублирует серверную, не заменяет её.
114. Незаинструментированные данные показывать «Pending», а не выдумывать.
115. Доступность — гейт релиза: семантика, клавиатура, фокус, контраст.

## Git и доставка

116. Trunk-based: короткоживущие ветки от `main` с именем `type/short-slug`; долгоживущих `develop`/`release` нет.
117. `main` защищён и всегда деплоится: прямых пушей нет, любое изменение приходит через PR.
118. PR маленький и с одной целью, с зелёным CI (линт, типы, тесты, дифф OpenAPI) и хотя бы одним ревью перед мерджем.
119. Только squash-merge: PR схлопывается в один Conventional-коммит; история линейная (без merge-коммитов; устаревшие ветки — rebase).
120. Релиз автоматический: semantic-release на push в `main` вычисляет версию SemVer и собирает неизменяемый образ (правило 102).
121. Собрать один раз, продвигать тот же артефакт: образ с мерджа идёт в staging, затем в production, и не пересобирается под окружение.
122. Окружения текут `local → staging → production`; отличаются только конфиг/секреты, подаваемые из окружения.
123. Staging деплоится автоматически; production — по явному ручному подтверждению, никогда не безнадзорным авто-пушем.
124. Миграции идут отдельным пред-деплойным шагом, обратно-совместимо (expand→contract), до того как новый код примет трафик.
125. Zero-downtime выкатка по readiness-пробе; старые и новые инстансы сосуществуют, поэтому релиз схемо-совместим с предыдущим.
126. Откат = переразвернуть предыдущий образ; разрушающая (contract) миграция выходит лишь через релиз после ухода использующего её кода — откат не требует отката схемы.
127. Каждый деплой прослеживается до коммита и тега версии; работающий артефакт идентифицируем.
128. Тулинг деплоя — рекомендация, а не правило; какой бы ни был, он соблюдает принципы выше (один артефакт, конфиг из окружения, expand→contract, выкатка по readiness, откат переразвёртыванием).
