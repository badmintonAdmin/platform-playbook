# Платформенные принципы (cross-cutting)

> Верхнеуровневый свод, общий для **всех** сервисов и клиентов платформы. Он задаёт
> границы, контракты и соглашения, которые обязаны соблюдать и backend, и frontend, и
> любой другой клиент (мобильное приложение, сторонние интеграции, CLI).
>
> Технологические детали backend — в [BACKEND_RULES.md](BACKEND_RULES.md),
> [BACKEND_RULES_PRODUCTION.md](BACKEND_RULES_PRODUCTION.md),
> [BACKEND_STRUCTURE.md](BACKEND_STRUCTURE.md). Клиентские — в
> [FRONTEND_STRUCTURE.md](FRONTEND_STRUCTURE.md). Этот документ — над ними и **имеет
> приоритет** при конфликте: если частное правило противоречит платформенному
> принципу, побеждает принцип (или частное правило исправляется).

---

## 1. API-first и multi-client

**Главный принцип платформы: API — это продукт, а не деталь одного фронта.**

Один и тот же HTTP API обслуживает **несколько независимых клиентов**: веб-фронт,
мобильное приложение, сторонние интеграции, внутренние сервисы. Из этого следует:

1. **Ни одного клиента API не считает «своим».** В API нет предположений «это дёргает
   наш Next.js». Нет эндпоинтов «под конкретную страницу», нет полей «потому что так
   удобно вот этому экрану». Контракт описывает **предметную область**, а не UI.
2. **Backend не знает про рендеринг.** Никакого HTML, никакой серверной вёрстки под
   клиента, никаких «положим сюда готовую строку для кнопки». Клиент сам решает, как
   показывать данные.
3. **Клиент не лезет в БД и не знает про слои backend.** Единственный контракт между
   клиентом и сервером — **опубликованный API** (см. §3). Клиент общается только через
   него, никаких прямых обращений к хранилищу.
4. **Контракт версионируется, а не ломается по-тихому.** У мобильного приложения
   пользователь может месяцами не обновляться — старая версия клиента должна продолжать
   работать. Несовместимое изменение = **новая версия пути** (`/api/v2/...`), см. §4.
5. **Форматы — машинные и стабильные.** Даты — ISO-8601 в UTC, деньги — целые
   минимальные единицы (копейки/центы) либо строкой с валютой, идентификаторы —
   стабильные и непрозрачные. Никакой локали/таймзоны/форматирования на стороне API —
   это ответственность клиента.

**Проверка при любом новом эндпоинте:** «Сможет ли это без боли вызвать мобильное
приложение и сторонняя интеграция, которых сейчас нет?» Если ответ зависит от знания
про конкретный фронт — эндпоинт спроектирован неверно.

## 2. Единая слоистая модель (сквозь всю платформу)

Границы одинаковы на всех уровнях: **зависимость направлена внутрь, к абстракции.**

```
┌──────────────────────────────────────────────────────────────┐
│  Клиенты (web / mobile / integrations)                        │
│      знают ТОЛЬКО опубликованный контракт API (§3)            │
├──────────────────────────────────────────────────────────────┤
│  Backend: Router → UseCase → Service → Repository → I/O       │
│      зависят от Protocol, не от реализации (см. BACKEND_RULES) │
└──────────────────────────────────────────────────────────────┘
```

- **Граница «клиент ↔ сервер»** = контракт API (§3). Пересекается только DTO.
- **Границы внутри backend** = слои чистой архитектуры (см.
  [BACKEND_RULES.md §4](BACKEND_RULES.md)).
- **Правило переносимости:** смена реализации по одну сторону границы не должна менять
  код по другую. Смена БД не трогает клиента; редизайн экрана не трогает API; смена
  фреймворка не трогает бизнес-логику.

---

## 3. Контракт API — единственный шов между клиентом и сервером

Контракт первичен и является **источником истины** для всех клиентов.

### Схема как контракт
- Backend публикует **OpenAPI-схему** (FastAPI генерирует её из Pydantic-DTO и роутов
  автоматически). Схема — артефакт релиза, а не побочный эффект.
- **Клиентские типы генерируются из OpenAPI**, а не пишутся руками. Расхождение типов
  между клиентом и сервером — это баг сборки, а не рантайма.
- Никакой клиент не хранит «своё представление» о полях сервера параллельно контракту.
- **Процесс, а не дисциплина:** сгенерированные типы коммитятся; CI проверяет их
  свежесть (регенерация + `git diff --exit-code`) и **ловит breaking change схемы на
  PR** (дифф OpenAPI против main), а не в проде.

### Casing на границе
- **Наружу (JSON API) — `camelCase`.** Внутри Python — `snake_case`. Конвертацию делают
  Pydantic-схемы (`alias_generator` + `populate_by_name`), а не ручной маппинг.
- Клиент работает с `camelCase` и **не переименовывает поля** под свои нужды.

### Единый формат ответа об ошибке
Все ошибки API — **один машинно-читаемый конверт**, одинаковый для всех клиентов:

```jsonc
{
  "error": "ModelNotFound",         // стабильный код класса ошибки (для ветвления в клиенте)
  "message": "User not found",       // человекочитаемое, НЕ для парсинга
  "details": { "field": "email" }    // опционально: контекст (какие поля, какие лимиты)
}
```

- HTTP-статус несёт семантику (404/403/409/422/429/5xx), тело — детали.
- **Клиент ветвится по `error` (коду), а не по `message`** — сообщение может меняться и
  локализоваться.
- Маппинг доменных ошибок → HTTP — централизованно на backend (см.
  [BACKEND_RULES.md §11](BACKEND_RULES.md)). Формат конверта един для всей платформы.

### Что API отдаёт, а что нет
- **Не отдаёт** внутренние сущности/ORM, технические поля, секреты, PII сверх нужного.
- **Отдаёт** DTO предметной области. Секреты — **write-only** (принимаются на запись,
  никогда не возвращаются; маскируются в ответах, логах, UI).

## 4. Версионирование и совместимость

- Путь версионируется префиксом: **`/api/v1/...`**.
- **Обратно-совместимые** изменения (добавление опционального поля, нового эндпоинта) —
  в текущей версии.
- **Несовместимые** (удаление/переименование поля, изменение типа, ужесточение
  валидации, смена семантики) — **новая версия пути**. Старая версия живёт до
  согласованного вывода из эксплуатации (у мобильных клиентов — с запасом).
- Правило совместимости — тот же SemVer-принцип, что и для кода (см.
  [BACKEND_RULES.md §14](BACKEND_RULES.md)): breaking → MAJOR → новая версия API.
- **Толерантный клиент:** клиенты игнорируют неизвестные поля в ответе (не падают на
  добавлении поля сервером). Это обязательное условие безопасной эволюции контракта.

## 5. Идентичность и сессии — сквозь все клиенты

Модель аутентификации должна работать **одинаково** для web и mobile (см. также
[BACKEND_RULES_PRODUCTION.md §1](BACKEND_RULES_PRODUCTION.md)).

- **Токеновая модель (JWT) как база для multi-client.** Короткий access-токен + refresh
  с ротацией и возможностью отзыва. Мобильные клиенты не умеют в cookie так, как браузер.
- **Web** может использовать httpOnly-cookie поверх той же токеновой модели; **mobile /
  интеграции** — `Authorization: Bearer`. Сервер принимает оба способа доставки одного и
  того же токена — но **это один механизм идентичности**, а не два параллельных.
- **Cookie-доставка тянет за собой CSRF-защиту:** `SameSite=Lax/Strict` на cookie +
  CSRF-токен на мутирующие запросы (double-submit или заголовок). Bearer-клиентов CSRF
  не касается — токен не отправляется браузером автоматически.
- **Авторизация (можно ли действие) — всегда на backend, в доменном слое.** Клиент может
  прятать кнопку, но решение принимает сервер. Ни один клиент не является доверенной
  границей.
- **Проверка владения ресурсом (object-level) — в каждом UseCase.** Аутентификация ≠
  право на конкретный объект (OWASP API #1, см. PRODUCTION §1–2).

---

## 6. Конфигурация и среды

- **12-factor:** конфигурация — из окружения, не из кода и не из репозитория. Один и тот
  же артефакт (образ/бандл) прогоняется по средам `local` → `staging` → `production`,
  меняется только конфиг.
- **В репозитории — только `.env.example`** (шаблон без значений). Реальные значения —
  из окружения; прод-секреты — из secrets-manager, не из файла на диске (PRODUCTION §14).
- **Ни один клиент не хардкодит базовый URL API** — только из конфигурации среды.
- Флаги фич и переключатели поведения — через конфиг/feature-flags, а не через ветки
  кода «под среду».

---

## 7. Наблюдаемость сквозь границы

- **Correlation / Request ID** проходит **через всю цепочку**: клиент генерирует или
  сервер присваивает `X-Request-ID`, он попадает в каждый лог-стейтмент, в ответ об
  ошибке и прокидывается в исходящие вызовы (см. PRODUCTION §3). По одному id можно
  собрать путь запроса от клиента до БД.
- **Структурные логи** (JSON), без PII/секретов, в stdout.
- **Продуктовая аналитика** (события пользователя) отделена от технической
  наблюдаемости (логи/метрики/трейсы) и не смешивается с ней.

---

## 8. Именование и словарь

- **Единый язык предметной области (ubiquitous language)** через всю платформу: одна
  сущность называется одинаково в БД, в DTO, в API-путях и в клиенте. `User` — везде
  `user`, а не `account` в одном месте и `member` в другом.
- Соглашения по коду каждого слоя — в соответствующих файлах (backend-нейминг в
  [BACKEND_STRUCTURE.md](BACKEND_STRUCTURE.md), API-пути и casing — здесь в §3).
- Границы предметных областей (**bounded contexts**) на backend = отдельные домены в
  `apps/` (см. [BACKEND_RULES.md §3](BACKEND_RULES.md)); их публичные части в API не
  протекают деталями реализации домена.

## 9. Калибровка масштаба

Платформа проектируется **большой по структуре, а не по нагрузке**. Расчётная точка —
**сотни пользователей, не миллионы**. Из этого следует:

- **Оптимизируем изменяемость и простоту, а не throughput.** Чистая архитектура,
  изоляция доменов и контракты — в полный рост (они про управляемость); горизонтальное
  масштабирование «как у больших» — нет.
- **Модульный монолит — дефолт.** Изоляция доменов (см. BACKEND_RULES §4) сохраняет
  возможность выделить сервис позже, но мы **не выделяем сервисы «на вырост»**.
- **Сервис выделяется только по сильной причине:** другой цикл релизов, изоляция
  отказов, принципиально другая технология/нагрузка. «Так моднее» причиной не является.
- **Не тащить тяжёлую инфраструктуру без нужды:** шардирование, мультирегион,
  кластеры, service mesh — оверкилл. PostgreSQL + Redis + один брокер закрывают
  потребности этого масштаба.
- Контрактные правила (§3–4, §10) при этом соблюдаются **в полном объёме** — они про
  эволюцию и совместимость, а не про нагрузку.

## 10. Контракты событий (брокер / очереди)

Если сервисы общаются через брокер (Kafka / RabbitMQ / NATS / Redis), **событие — такой
же публичный контракт, как HTTP API**, с той же строгостью к схеме и совместимости.

### Схема и нейминг
- Payload события — **версионируемая Pydantic-схема**, живёт в домене-продюсере
  (`apps/<domain>/events.py`). Консьюмер зависит **только от схемы события**, не от
  внутренностей продюсера.
- Имя события: `<domain>.<entity>.<action>` в **прошедшем времени** — событие
  описывает свершившийся факт, не команду: `orders.order.created`,
  `users.user.deactivated`.
- Эволюция схемы — **только аддитивная** (новые опциональные поля). Breaking change =
  **новая версия события** (`orders.order.created.v2`); старая живёт, пока есть
  консьюмеры.

### Конверт события
Каждое сообщение несёт стандартный конверт:

```jsonc
{
  "messageId": "0195…",          // UUID — для дедупликации консьюмером
  "eventName": "orders.order.created",
  "eventVersion": 1,
  "occurredAt": "2026-07-02T12:00:00Z",   // UTC, момент факта
  "correlationId": "…",           // сквозной id цепочки (см. §7)
  "payload": { … }                // версионируемая схема
}
```

### Надёжность (см. PRODUCTION §9, §11)
- Публикация — **только через Transactional Outbox** (в одной транзакции с доменным
  изменением); dual-write запрещён.
- Доставка — at-least-once ⇒ **каждый консьюмер идемпотентен** (дедуп по `messageId`);
  «ядовитые» сообщения — в DLQ с retry/backoff.

## Сводка платформенных «do / don't»

**DO**
- Проектировать API от предметной области, а не от экрана; держать его пригодным для
  мобильного и стороннего клиента с первого дня.
- Единственный контракт клиент↔сервер — опубликованный OpenAPI; типы клиента —
  генерируются из него.
- `camelCase` на границе, единый конверт ошибки, ветвление клиента по коду ошибки.
- Версионировать API по пути; клиенты толерантны к неизвестным полям.
- Одна токеновая модель идентичности для всех клиентов; авторизация — на сервере.
- Конфиг из окружения; correlation id сквозь всю цепочку.

**DON'T**
- Лепить эндпоинты «под страницу»; возвращать готовую вёрстку/локализованные строки.
- Давать клиенту знать про слои/БД backend в обход API.
- Ломать контракт без новой версии; ветвить клиент по тексту сообщения об ошибке.
- Держать две параллельные модели аутентификации для web и mobile.
- Хардкодить базовый URL API; возвращать секреты/ORM-сущности наружу.
