# Структура frontend (эталонная)

> Каноническая структура и базовые правила web-клиента платформы (Next.js App Router).
> Frontend — **один из клиентов** общего API (наравне с мобильным приложением и
> интеграциями), поэтому он подчиняется платформенному контракту из
> [PLATFORM.md](PLATFORM.md): общается только через опубликованный API, типы генерирует
> из OpenAPI, использует `camelCase` и единый конверт ошибки.
>
> Стек: Next.js App Router + TypeScript. Стилевая система и библиотека компонентов —
> определяются продуктом; правила ниже от них не зависят. Пакетный менеджер — pnpm.
>
> Это baseline. Глубокие правила (state, data fetching, формы, перформанс, a11y) будут
> дополняться отдельно.

---

## 1. Frontend — клиент, а не «пара к бэкенду»

- Web-фронт **не привилегирован**: API его не знает и не подстраивается под его экраны
  (см. [PLATFORM.md §1](PLATFORM.md)). Всё, что нужно фронту, он получает через тот же
  контракт, что и мобильное приложение.
- **Единственный контракт — опубликованный API.** Никаких прямых обращений к БД, к
  внутренним сервисам, к слоям backend в обход API.
- **Типы DTO генерируются из OpenAPI-схемы backend**, не пишутся руками. Ручной тип,
  дублирующий контракт, — источник рассинхрона.
- Логика авторизации — на сервере. Фронт может прятать элемент по роли, но **не считает
  это защитой** (см. [PLATFORM.md §5](PLATFORM.md)).

---

## 2. Surfaces: несколько поверхностей, одна оболочка

Приложение может иметь **несколько поверхностей** (surfaces) с разной аудиторией и
назначением, разделяющих общую dashboard-оболочку. Держи их концептуально и структурно
раздельными.

Типовой паттерн:

| Surface | Маршрут | Аудитория | Назначение |
|---|---|---|---|
| **Пользовательская** | `/app` | обычный пользователь | управление своими данными |
| **Админская** | `/app/admin` | оператор/владелец аккаунта | управление приложением в рамках аккаунта |

Принципы:
- **Одна поверхность = одна ответственность.** Не смешивать пользовательские функции с
  административными в одном экране.
- **Видимость поверхности гейтится ролью**, а backend **обязательно** проверяет доступ
  на своей стороне (гейт на фронте — только UX, не безопасность).
- Если понадобится **кросс-аккаунтная операторская консоль** — это **отдельная, третья**
  поверхность, а не примесь к существующим.

## 3. Структура маршрутов (App Router route groups)

Route-группы `( … )` организуют код, не меняя URL. Публичное и защищённое — явно.

```
app/
├── (marketing)/        # PUBLIC — лендинги (много; часто редактируемые, вкл. AI-агентом; /, /l/[slug])
├── (auth)/             # PUBLIC — минимальный auth layout (login / signup / …)
├── (app)/              # PROTECTED (middleware) — dashboard-оболочка
│   ├── layout.tsx      #   гварды + chrome оболочки
│   ├── app/            #   пользовательская поверхность (/app)
│   └── app/admin/      #   админская поверхность (/app/admin)
├── api/                # route handlers (BFF: только там, где нужен серверный посредник)
├── layout.tsx          # корневой layout
└── globals.css         # глобальные стили (если модель стилей — глобальная)
```

- Один dashboard-маршрут, без задвоенных/нетипичных сегментов (не плодить `/dashboard`
  и `/app` одновременно).
- `middleware.ts` защищает protected-группу → неаутентифицированного на
  `/login?return_to=…`.
- `app/api/` (route handlers) — **только как BFF-посредник** (проксирование секрета,
  агрегация под SSR). Бизнес-логику туда не переносить: она живёт в backend.
- **Публичные лендинги** (`(marketing)`) изолированы от `(app)`: не импортируют
  dashboard-код, сессии, права; их можно вынести в отдельный деплой позже. Лендинг —
  тонкая презентация + вызов **стабильного** публичного эндпоинта приёма лидов
  (форма → `apiFetch` → `POST /leads`). Логика приёма — на бэкенде; правка лендинга
  (в т.ч. AI-агентом) не трогает контракт. Визуальный конструктор/CMS не вводится.

## 4. Границы рендеринга (Server / Client Components)

- **По умолчанию — Server Component.** `"use client"` — только там, где нужна
  интерактивность/браузерные API (state, эффекты, обработчики).
- Клиентскую границу держать **как можно ниже** по дереву (листовые интерактивные
  компоненты), чтобы не утягивать в клиент лишнее.
- **Секреты и приватные ключи — только на сервере.** В клиентский бандл не должно
  попадать ничего, кроме публичной конфигурации (`NEXT_PUBLIC_*`).
- Данные грузить как можно ближе к месту использования; не прокидывать серверные объекты
  в клиент без необходимости.

## 5. Организация компонентов

```
components/
├── ui/          # общие презентационные примитивы (Button, Card, Modal, …) —
│                #   тонкие обёртки над стилевой системой, без бизнес-логики
├── <surface>/   # компоненты секций конкретной поверхности (dashboard, admin, …)
└── landing/     # секции маркетинговых страниц
```

- Общее → `ui/`. Специфичное для поверхности → в её папку.
- **Страницы тонкие**: композируют компоненты, не содержат бизнес-логики и прямых
  fetch'ей вразнобой.
- `ui/`-примитивы не знают про предметную область (переиспользуемы между поверхностями).

### Гранулярность (анти-god-файлы)

- **Один компонент = один файл; файл ≤ 300 строк — CI-гейт** (сгенерированное —
  allowlist). Страница — тонкая композиция, ориентир ≤ 150 строк.
- Компонент оброс состоянием/логикой — логика выносится в **hook отдельным файлом**
  (`use-<name>.ts`), не раздувает JSX.
- **Catch-all `utils.ts` запрещён**: `lib/` — модули по смыслу (`lib/format-money.ts`,
  `lib/date.ts`), а не свалка.

## 6. `lib/` — инфраструктура клиента

- **`lib/env.ts`** — единый источник базового URL API (server `API_URL` / browser
  `NEXT_PUBLIC_API_URL`). **Никогда** не хардкодить базу API в странице/компоненте
  (см. [PLATFORM.md §6](PLATFORM.md)).
- **`lib/api-client.ts`** — **единственный** `apiFetch`: через него идут **все** вызовы
  API. Он централизует:
  - доставку идентичности (cookie/Bearer — см. [PLATFORM.md §5](PLATFORM.md));
  - разбор **единого конверта ошибки** (`error`/`message`/`details`) → типизированная
    ошибка клиента;
  - ветвление по **коду** `error`, не по тексту `message`;
  - реакцию на `401` (→ `/login`) и проброс `X-Request-ID` (см. PLATFORM §7).
- **`lib/types.ts`** — DTO, **сгенерированные** из OpenAPI backend (не дубли руками).
- **`lib/session.ts`** — хелперы текущего пользователя/сессии.
- **`lib/validation.ts`** — валидация форм (zod или аналог) с понятными сообщениями;
  клиентская валидация **дублирует**, а не заменяет серверную.

## 7. Данные, ошибки, формы (baseline)

- **Data fetching** идёт только через `apiFetch`. Никаких «голых» `fetch` с ручным
  URL/casing по компонентам.
- **Серверные данные не дублируются в глобальном сторе.** Выбирается **один** механизм
  серверного состояния на проект (RSC-fetch и/или query-библиотека с кэшем и
  ревалидацией) — и все данные API живут в нём. Глобальный клиентский стор — только
  для чистого UI-состояния (открытые панели, черновики форм), не для копий ответов API.
- **Обработка ошибок** опирается на единый конверт: показываем пользователю
  человекочитаемое, ветвим логику по коду. Неизвестные поля ответа игнорируем
  (толерантный клиент, PLATFORM §4).
- **Формы**: клиентская валидация для UX + доверие серверной как источнику истины;
  ошибки полей маппятся из `details` конверта.
- **Секреты в UI — write-only**: маскируются, пустое поле сохраняет прежнее значение,
  «сырые» ключи не показываются и не логируются (см. PLATFORM §3).
- **Незаинструментированные данные** (метрики/цифры, которых ещё нет) показывать как
  «Pending», а не выдумывать значения.

---

## 8. Доступность (baseline)

- Семантический HTML, доступные с клавиатуры интерактивы, корректные `aria-*`, видимый
  фокус, достаточный контраст.
- Формы: связанные `label`, понятные сообщения об ошибке, состояние загрузки/ошибки
  озвучивается ассистивным технологиям.
- Доступность — **гейт релиза**, а не украшение (продукт может ужесточать этот раздел).

## Сводка frontend «do / don't»

**DO**
- Ходить в API только через единый `apiFetch`; типы — из OpenAPI; `camelCase` на границе.
- Держать поверхности раздельно; видимость гейтить ролью (защита — на backend).
- Server Component по умолчанию; клиентскую границу — ниже по дереву.
- Единый конверт ошибки, ветвление по коду; секреты write-only; a11y как гейт.
- База API — из конфигурации среды.

**DON'T**
- Обращаться к БД/внутренним слоям в обход API; считать фронт-гейт защитой.
- Дублировать DTO руками; ветвиться по тексту сообщения об ошибке.
- Хардкодить базовый URL API; тащить секреты/серверные объекты в клиентский бандл.
- Складывать бизнес-логику в страницы или в `app/api/` BFF.
